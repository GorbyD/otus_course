
# 1. Модульные тесты

## 1.1 Бэк — валидация входных данных

**`card_number`**
- Содержит не цифры → 400, сообщение об ошибке в поле `card_number`;
- Длина не равна 16 (короче/длиннее) → 400;
- Поле отсутствует / пустая строка → 400.

**`card_holder`**
- Содержит более одного пробела → 400;
- Нет пробела  → 400;
- Содержит цифры или спецсимволы, кроме дефиса → 400;
- Содержит символы, отличные от латиницы → 400;
- Пустая строка → 400;


**`card_expiration`**
- Неверный формат (не `мм/гг`) → 400;
- Месяц вне диапазона `01`–`12` → 400;
- Срок действия карты уже истёк → 400.

**`cvv`**
- Содержит нецифровые символы → 400;
- Длина не равна 3 → 400;
- Пустое значение → 400.

**`order_number`**
- Длина больше 16 символов → 400;
- Пустая строка / поле отсутствует → 400.

**`sum`**
- Дробная часть отделена точкой, а не запятой → 400;
- Значение ≤ 0 → 400;
- Не является числом (буквы, спецсимволы) → 400;
- Пустая строка → 400.

**Позитивный кейс**
- Все поля валидны → метод не возвращает 400 и передаёт в клиент сервиса A ровно те
  данные, что пришли на вход

## 1.2 Бэк
Данные для валидации всегда валидны

- Клиент сервиса A возвращает 403 → метод возвращает ошибку платежа на фронт (код/сообщение, например 402), репозиторий не вызывается
- Клиент сервиса A возвращает 200 → метод вызывает `repository->setOrderIsPaid($order_number, $sum)` ровно один раз с полученными из запроса `order_number` и числовым `sum`, и при `true` возвращает на фронт успешный ответ (200)
- `setOrderIsPaid` бросает исключение (например, сумма не совпала с суммой заказа в БД) → метод перехватывает исключение и возвращает на фронт код серверной ошибки (например 500).
- Клиент сервиса A не отвечает и истекает настроенный таймаут ожидания (мок бросает исключение таймаута/connection timeout) → метод не виснет, возвращает на фронт код «сервис недоступен» (например 502/504), репозиторий не вызывается;
- Клиент сервиса A возвращает недопустимый ответ — 5xx или тело, не являющееся ожидаемым JSON (мок отдаёт битый payload) → метод считает отказом сервиса A, возвращает на фронт код ошибки, репозиторий не вызывается =

## 1.3 Репозиторий — `setOrderIsPaid`
БД замокана/подставлена in-memory реализация — проверяем только логику метода.

- Номер заказа найден, сумма совпадает с суммой заказа в БД → возвращает `true`, статус заказа в БД помечается оплаченным;
- Заказ с таким `order_number` не найден → выбрасывает исключение (`OrderNotFoundException`);
- Заказ найден, но переданная сумма не совпадает с суммой заказа → выбрасывает исключение (`SumMismatchException`);
- Заказ уже помечен оплаченным ранее (повторный вызов) → выбрасывает исключение, чтобы не задвоить оплату при повторной отправке запроса сервисом A/ретраях.

## 1.4 Фронт — реакция на ответы бэка
проверяем только логику отображения по уже полученному ответу.

- Получен 400 с указанием проблемного поля (например `card_number`) → у соответствующего поля формы появляется красная рамка и текст ошибки, остальные поля не подсвечиваются;
- Получен 200 → пользователю показывается сообщение об успешной оплате;
- Получен код ошибки платежа сервиса A, протранслированный бэком (например 402) → показывается общее сообщение о неудачном списании без привязки к конкретному полю формы.

# 2. Интеграционные тесты
## 2.1 фронт-бэк
Бэк работает как чёрный ящик, проверяется реальный HTTP-обмен фронт-бэк.

1. `card_holder` содержит более одного пробела → после ответа от бэка на фронте поле «Владелец карты» выделяется красной рамкой с текстом ошибки (пример из задания);
2. Все поля валидны, сервис A "успех" → бэк отвечает 200, фронт показывает сообщение об успешной оплате;
3. Все поля валидны, сервис A "отказ" → бэк отвечает кодом ошибки платежа, фронт показывает общее сообщение о неудачном списании (без рамки на конкретном поле).

## 2.2 бэк-репозиторий
Сервис A замокан на «успешное списание».

1. Заказ с ожидаемым `order_number` и суммой существует в тестовой БД → после запроса бэк отвечает 200, а запись о заказе в БД помечается оплаченной (проверяется прямым чтением из тестовой БД);
2. `sum`, пришедший от фронта, не совпадает с суммой заказа в тестовой БД → репозиторий бросает исключение, бэк отвечает кодом серверной ошибки (500).
3. Два одновременных запроса на оплату одного заказа (одинаковые `order_number` и `sum`) отправляются параллельно бэку, который обращается к реальной тестовой БД → только один запрос получает `true` от репозитория и 200 на фронт, второй получает исключение и код ошибки, а в БД остаётся одна отметка об оплате.

## 2.3 бэк-сервис A

Репозиторий замокан

1. Валидные данные, тестовая карта сервиса A, гарантированно завершающая списание успехом → сервис A отвечает 200, бэк инициирует вызов замоканного репозитория;
2. Валидные данные, тестовая карта sandbox-режима, гарантированно отклоняемая сервисом A → сервис A отвечает 403, бэк отвечает фронту кодом ошибки платежа, репозиторий не вызывается.
3. Сервис A задерживает ответ дольше настроенного таймаута бэка → бэк не виснет, по истечении своего таймаута отвечает фронту кодом «сервис недоступен», к репозиторию не обращается;
4. Сервис A отвечает 5xx или телом не являющимся JSON → бэк отвечает фронту кодом ошибки, не считает непонятный ответ успехом, к репозиторию не обращается.

# 3. Системные тесты
реальный фронт → реальный бэк → реальная тестовая БД → сервис A в sandbox-режиме.

1. Пользователь вводит полностью валидные данные с тестовой картой sandbox-режима, гарантирующей успех → в итоге на фронте отображается сообщение об успешной оплате, а в БД появляется запись об оплаченном заказе — это ключевой кейс, подтверждающий, что весь путь пользователя до цели («оплатить и посмотреть фильм») работает;
2. `cvv` неверен → после ответа бэка на фронте выводится сообщение «Не удалось списать данные с карты, проверьте реквизиты»;
3. Пользователь вводит данные с тестовой картой sandbox-режима, гарантированно отклоняемой сервисом A (например «недостаточно средств»), фронт показывает сообщение о неудачном списании, а запись в БД не помечается оплаченной;
4. Пользователь вводит невалидные данные прямо на фронте (например, пустой `card_number`) → сообщение об ошибке валидации и красная рамка вокруг поля «Номер карты» отображаются сразу, до какого-либо обращения к сервису A.
6. Пользователь дважды подряд быстро нажимает «Оплатить» по одному и тому же заказу (двойной клик/повторная отправка формы до получения первого ответа) → в БД должна появиться одна запись об оплате, а фронт в итоге должен показать пользователю одно сообщение об успехе, не показать ошибку по второму запросу как будто что-то сломалось

# 4. Тестирвование реальными деньгами
Так как успешное списание через сервис A в проде — это движение денег, прогон интеграционных (бэк-сервис A) и системных тестов на боевом контуре будет стоить реальных денег при каждом запуске. Для удешевления:

- Использовать sandbox/тестовый режим сервиса A с выделенными тестовыми номерами карт, гарантированно возвращающими 200 или 403 без реального движения денег;
- Для связки «бэк-репозиторий» вообще не обращаться к сервису A — полностью подменять его моком, поскольку цель этих тестов не имеет отношения к реальному списанию;
- Использовать заведомо фиксированные тестовые `order_number`, чтобы повторные прогоны не плодили новые реальные списания и было легко отличить тестовые записи от боевых при последующей очистке.
- очистка: тестовые заказы должны удаляться (или помечаться отдельным флагом `is_test`, исключающим их из прод-отчёта) в teardown теста сразу после прогона. Может стоит завести периодический таск на тестовом окружении, который чистит записи.
